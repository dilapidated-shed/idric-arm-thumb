# E3M2: OCP FP6 element format

## Exact upstream reference

Open Compute Project, *OCP Microscaling Formats (MX) Specification*,
Version 1.0, September 2023:

https://www.opencompute.org/documents/ocp-microscaling-formats-mx-v1-0-spec-final-pdf

E3M2 is one of the two FP6 element encodings used by MXFP6. This file specifies
the scalar E3M2 element encoding itself. MX block scaling is a separate layer.

## Storage

E3M2 occupies exactly 6 bits:

```text
bit 5       bits 4..2       bits 1..0
+------+----------------+---------------+
| sign | exponent: 3    | mantissa: 2   |
+------+----------------+---------------+
```

Let:

- `S` be the sign bit;
- `E` be the unsigned 3-bit exponent field;
- `M` be the unsigned 2-bit mantissa/trailing-significand field;
- exponent bias = 3.

## Values

### Normal numbers

For `E > 0`:

```text
value = (-1)^S * 2^(E - 3) * (1 + M / 4)
```

Unlike IEEE-style formats, E3M2 reserves no exponent pattern for infinity or
NaN. Therefore `E = 7` is an ordinary finite exponent.

### Subnormal numbers

For `E = 0` and `M != 0`:

```text
value = (-1)^S * 2^(1 - 3) * (M / 4)
      = (-1)^S * 2^-2 * (M / 4)
```

### Zeros

```text
S 000 00
```

Both sign-bit encodings exist, giving signed zero encodings.

## Boundary values

```text
minimum positive subnormal = 0.0625
maximum subnormal          = 0.1875
minimum positive normal    = 0.25
maximum finite magnitude   = 28.0
```

Maximum finite encoding:

```text
S 111 11 = +/- 2^4 * 1.75 = +/- 28
```

## No infinity or NaN encoding

E3M2 has no reserved bit pattern for infinity and no reserved bit pattern for
NaN.

## Conversion requirements from the OCP MX specification

An implementation converting a wider value to FP6 E3M2 must support:

- subnormals;
- round-to-nearest, ties-to-even;
- saturation/clamping of post-rounding overflow to the maximum finite magnitude,
  preserving sign;
- conversion to zero when the magnitude is below the minimum subnormal after
  rounding.

Conversion from a source NaN is implementation-defined. Additional rounding or
overflow modes may exist, but the behavior above is the required baseline.

## Scalar arithmetic

The E3M2 element-format definition does not by itself define a scalar
add/multiply/divide arithmetic contract. Arithmetic policy in this backend must
therefore be specified separately from the encoding.

## Dense and register representation

The interchange payload is 6 bits. A Thumb scalar implementation may hold that
payload in the low six bits of a byte or word register. The two unused container
bits are not part of E3M2.
