# E5M3: Ootomo-Naruse unsigned 8-bit storage format

## Exact upstream reference

Hiroyuki Ootomo and Akira Naruse,
*Custom 8-bit floating point value format for reducing shared memory bank
conflict in approximate nearest neighbor search*, arXiv:2301.06672:

- paper: https://arxiv.org/abs/2301.06672
- PDF: https://arxiv.org/pdf/2301.06672
- DOI: https://doi.org/10.48550/arXiv.2301.06672

This E5M3 is **not** a signed 1+5+3 nine-bit float. It is an unsigned 8-bit
storage format with five exponent bits and three mantissa bits.

## Purpose and scope

The paper defines E5M3 for compact storage of values known to be nonnegative.
It is designed for cheap conversion to and from FP32. It is explicitly a
storage format, not an arithmetic format.

The paper specifies:

- no sign bit;
- no subnormal/non-normalized numbers;
- no infinity encoding;
- no NaN encoding;
- no arithmetic directly between E5M3 values.

Behavior for negative values, zero as a distinguished IEEE-style value,
subnormals, infinities, NaNs, and out-of-range inputs is therefore outside the
defined source domain rather than something this repository should invent and
attribute to the paper.

## Storage

```text
bit 7                bit 3 bit 2              bit 0
+------------------------+-------------------------+
| exponent: 5 bits       | mantissa: 3 bits        |
+------------------------+-------------------------+
```

Let `E` be the unsigned five-bit exponent field and `M` the unsigned
three-bit mantissa field.

The exponent is aligned with IEEE binary16's five-bit exponent by using bias 15.

## FP32 -> E5M3 reference conversion

For a supported positive normal FP32 input, the paper's Figure 3 implements the
conversion by reinterpreting the FP32 bits as an unsigned integer, removing the
FP32-to-E5M3 exponent-bias difference, and retaining the upper eight payload
bits:

```text
u = bits32(x)
u = u - 0x38000000       # (127 - 15) << 23
code = (u >> 20) & 0xff
```

This is a truncating storage conversion over the domain the paper uses.

## E5M3 -> FP32 reference conversion

The paper's Figure 4 restores the exponent bias after shifting the E5M3 payload
back into the FP32 exponent/mantissa position and inserts a midpoint rounding
bit in the first discarded mantissa position:

```text
u = (uint32(code) << 20) + 0x38080000
x = fp32_from_bits(u)
```

Equivalently, for code fields `E` and `M`, the representative FP32 value
produced by that conversion is:

```text
2^(E - 15) * (1 + M/8 + 1/16)
```

The `1/16` term is the midpoint/rounding bit shown in the paper's conversion
figure. It is part of this particular storage conversion recipe; it should not
be silently generalized into IEEE-style E5M3 semantics.

## Consequence

All 256 payload patterns are ordinary storage codes in this scheme. There are
no reserved sign, infinity, NaN, or subnormal encodings.

The paper notes that this E5M3 range covers the full range of normalized FP16
values while using fewer mantissa bits.

## Arithmetic

None is specified. If this backend later defines scalar E5M3 arithmetic, that
will be a new local arithmetic contract built on top of this storage format,
not something claimed to come from Ootomo and Naruse.
